Terraform — Infrastructure as Reviewable Code
The diff engine that makes infrastructure changes as reviewable, auditable, and reversible as application code
🔄

Terraform is a diff engine for infrastructure. You declare what you want (HCL files). Terraform compares it against what you have (state file). It shows you exactly what will change — additions in green (+), modifications in yellow (~), destructions in red (-). You review and approve. Then it applies. This is git diff for cloud infrastructure — and it enables the same collaborative, reviewable workflow that code review enabled for application code.

1 · The Infrastructure Diff Engine

🧠
Mental Model — Git Diff for Cloud

You write *.tf files (desired state). Terraform reads them, reads the state file (actual known state), queries the cloud provider for real current state, and computes the diff. The terraform plan output is that diff: exactly what will be created, modified, or destroyed. Before applying, you read this diff the same way you read a pull request diff — checking for unintended changes, understanding the blast radius, and confirming the change matches the intent.

ClickOps — before Terraform
1. Log into AWS Console
2. Click: Create VPC → subnets × 6
   → Internet Gateway → Route tables
   → Security groups...
3. Hours later: env created
4. No record of what was created
5. Try to recreate staging: start over
6. Staging drifts from prod over time
Terraform IaC — after
1. Write HCL describing desired infra
2. terraform plan  → see exact changes
3. terraform apply → infra created
4. git commit      → infra versioned!
5. staging: workspace new staging
   && terraform apply → identical
6. Any drift: terraform plan detects it

3 · HCL Deep Dive

# ── variables.tf ──────────────────────────────────────────────
variable "environment" {
  description = "dev | staging | production"
  type        = string
  validation {
    condition     = contains(["dev", "staging", "production"], var.environment)
    error_message = "Must be dev, staging, or production."
  }
}

# ── locals.tf ─────────────────────────────────────────────────
locals {
  name_prefix  = "myapp-${var.environment}"
  common_tags  = {
    Environment = var.environment
    ManagedBy   = "terraform"
    Owner       = "platform-team"
  }
}

# ── main.tf ───────────────────────────────────────────────────
resource "aws_vpc" "main" {
  cidr_block           = "10.0.0.0/16"
  enable_dns_hostnames = true
  tags = merge(local.common_tags, { Name = "${local.name_prefix}-vpc" })
}

# for_each: create N resources from a map — safer than count
resource "aws_subnet" "private" {
  for_each = {
    "a" = "10.0.1.0/24"
    "b" = "10.0.2.0/24"
    "c" = "10.0.3.0/24"
  }
  vpc_id            = aws_vpc.main.id   # ← implicit dependency on vpc
  cidr_block        = each.value
  availability_zone = "${var.aws_region}${each.key}"
  tags = merge(local.common_tags, { Name = "${local.name_prefix}-private-${each.key}" })
}

# module: reuse a packaged group of resources
module "eks" {
  source  = "terraform-aws-modules/eks/aws"
  version = "~> 19.0"       # ✓ pinned to major version

  cluster_name    = "${local.name_prefix}-eks"
  vpc_id          = aws_vpc.main.id
  subnet_ids      = [for s in aws_subnet.private : s.id]

  eks_managed_node_groups = {
    general = { instance_types = ["t3.medium"], min_size = 2, max_size = 10 }
  }
  tags = local.common_tags
}

# outputs.tf — exported values for other stacks
output "cluster_endpoint" {
  value     = module.eks.cluster_endpoint
  sensitive = true  # ✓ hidden in logs
}

4 · State — The Most Critical File

🚨
Losing the state file is catastrophic

Terraform state maps your HCL resource addresses to real cloud resource IDs: aws_vpc.main → vpc-0a1b2c3d. Without state, Terraform thinks nothing exists and tries to create everything — resulting in duplicate resources, failed creates (some cloud resources enforce unique names), and an infrastructure your code no longer matches. Recovery requires terraform import for every resource — potentially days of work for large infrastructure.

# ✅ REQUIRED: remote state with locking in production
terraform {
  backend "s3" {
    bucket         = "mycompany-terraform-state"
    key            = "production/eks/terraform.tfstate"
    region         = "us-east-1"
    encrypt        = true                 # ✓ AES-256 at rest
    dynamodb_table = "terraform-state-lock"  # ✓ prevent concurrent applies
  }
}

7 · Terraform in CI/CD — Atlantis

💡
The GitOps Model for Infrastructure

Atlantis is the missing piece: it runs terraform plan automatically on every PR and posts the output as a comment. Engineers review the plan diff — "this will create 3 EC2 instances and delete 1 S3 bucket" — just like reviewing a code diff. Comment atlantis apply to apply. No one runs terraform apply locally on production. Every infrastructure change is: proposed → planned → reviewed → applied → logged. This is the same workflow application code goes through. The audit trail is the PR history.

8 · The 10 Commandments of Terraform at Scale

  • Remote state always — S3 + DynamoDB locking; never commit terraform.tfstate to Git
  • Module everything repeated — reuse a resource pattern >1 time? Make a module
  • Separate state by blast radius — VPC (monthly change) ≠ apps (daily change): separate state files
  • Pin provider and module versions — ~> 5.0 not > 5.0; commit .terraform.lock.hcl
  • No secrets in Terraform variables or state — use data sources to read from Vault/Secrets Manager
  • Plan before apply — always — terraform plan -out=tfplan; terraform apply tfplan
  • Tag everything — Environment, Owner, ManagedBy=terraform, CostCenter
  • Drift detection on a schedule — daily terraform plan in CI; alert on unexpected output
  • prevent_destroy on critical resources — prevent accidental destruction of prod databases
  • Atlantis or equivalent for production — no local applies; all changes through PR workflow
✅
Chapter Takeaways
  • Terraform is a diff engine — desired (HCL) vs actual (state) → plan → apply
  • State is the most critical file; lose it and you lose control of your infrastructure
  • for_each over count for creating multiple resources — removing a middle element doesn't renumber others
  • Modules are functions for infrastructure — extract repeated patterns, version them
  • GitOps via Atlantis: infrastructure PRs reviewed like code PRs, complete audit trail
  • OIDC for cloud auth in CI — no AWS keys stored anywhere in your pipeline
