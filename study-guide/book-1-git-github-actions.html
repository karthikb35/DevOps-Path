1 · Git Internals — The Content-Addressed DAG

🧠
Mental Model — The Immutable Ledger

Git is like a bank ledger: every entry is permanent and chained to the previous one. You cannot change a past transaction — you can only add new ones. Each commit's SHA is a cryptographic hash of its entire content plus its parent's SHA. If anyone alters a single byte in history, every subsequent SHA changes. Tampering is physically detectable.

What

Git is a content-addressed key-value store layered on a directed acyclic graph of commits. The key is a SHA-1 hash of the content; the value is one of four object types: blob (file content), tree (directory listing of blobs and sub-trees), commit (pointer to a tree + metadata + parent commits), tag (annotated pointer to a commit).

Why it matters

Because the content-addressed model gives you integrity, deduplication, and cheap branches — all as emergent properties of the design, not as added features. A branch is a 40-byte pointer. Identical files across commits share one blob object. History cannot be silently rewritten. These properties underpin every collaborative workflow.

How — Object Graph Walkthrough

When you run git commit, Git:

  1. Hashes each changed file → new blob objects
  2. Hashes the directory tree → new tree object (unchanged files reuse existing blobs)
  3. Hashes the commit (author + timestamp + tree SHA + parent SHA) → commit object
  4. Moves the current branch pointer to the new commit SHA

The SHA chain means: change any file → new blob → new tree → new commit → different SHA. History is verified by re-hashing.

When it matters operationally

Understanding the object model explains why git push --force on a shared branch is destructive (it orphans commits others have built on), why git rebase rewrites SHAs (new commit objects with different parent chains), and why the reflog is your safety net (orphaned objects survive for ~30 days).

The Three Trees — Git's Most Misunderstood Model

Engineers who understand "add, commit, push" but not the three trees are perpetually confused by git reset, git restore, and merge conflicts. The three trees are three separate views of your repository state that Git keeps in sync:

TreeWhat it holdsHow to move itCommand to inspect
HEADLast commit snapshotgit commitgit show HEAD
Index (Staging)Proposed next commitgit addgit diff --staged
Working DirectoryActual files on diskEditing filesgit diff
🔎
Why git reset has three modes

git reset --soft HEAD~1 moves only HEAD (undoes the commit, keeps staged changes). git reset HEAD~1 moves HEAD + resets the index (undoes commit AND unstages, keeps working dir). git reset --hard HEAD~1 moves all three trees (destroys working dir changes). The three-tree mental model makes this immediately obvious — you're choosing how many trees to move.

The Reflog — Git's Safety Net

⚠️
Gotcha — "I destroyed my work with git reset --hard"

Nothing is truly lost in Git for ~30 days. The reflog records every movement of HEAD. After a bad git reset --hard: run git reflog to find the SHA you were at, then git checkout -b recovery <sha> to recover it. The orphaned commits still exist in .git/objects until garbage collection runs. Engineers who know the reflog have a superpower their colleagues lack.

Before — Panic
$ git reset --hard HEAD~3
$ # "Oh no, I lost 3 commits of work!"
$ git log --oneline
a3f4b1c  Initial commit
# The commits seem gone...
After — Reflog Recovery
$ git reflog
d5e6f7a HEAD@{0}: reset: moving to HEAD~3
c3b2a1f HEAD@{1}: commit: Add payment module
b2a1c9e HEAD@{2}: commit: Add user service
...
$ git checkout -b recovery c3b2a1f
# All 3 commits recovered ✓
Q · Why does changing a single byte in a file change the entire commit chain?

Because Git uses content-addressing: each object's identity IS its SHA hash of its content. Change a file → new blob SHA → the tree that references that blob gets a new SHA → the commit that references that tree gets a new SHA. The chain is cryptographic: every SHA is a hash of the content including all the SHAs it points to. This is why Git history can be verified and why git push --force on a shared branch is dangerous — it orphans all commits that pointed to the old chain.

Q · What is git bisect and why is it O(log n)?

Git bisect finds the commit that introduced a bug by binary search through the commit DAG. You mark a known-good commit and the current bad commit. Bisect picks the midpoint, you test it and mark it good or bad. This halves the search space each step. For 1,000 commits, that's ≤10 tests instead of up to 1,000. It leverages the immutable DAG structure — each commit is uniquely identifiable by its SHA, and you can checkout any commit in O(1). The algorithm is: while (hi - lo) > 1: mid = (lo+hi)/2; test(mid) → update lo or hi.

🌍
Real-World: Linux Kernel — 1,000+ Contributors, Zero Tampered Commits

The Linux kernel receives patches from engineers worldwide whom Linus Torvalds has never met. Because every patch is identified by its SHA, Linus can accept code knowing that the bytes he receives are exactly what was sent — no manipulation in transit, no hidden changes. The cryptographic chain extends through the entire history: any tampering with any file in any commit would change every subsequent SHA. Git's object model is the Linux kernel's distributed trust system. As of 2026, the kernel repo has 1.2M commits and has never had a verified case of undetected history tampering.

2 · Branching Strategies at Scale

🧠
Mental Model — The Blast-Radius Dial

Every branching strategy is a dial between two extremes: maximum isolation (long-lived branches, protected from others' work) and maximum integration speed (trunk-based, work is always merged). Turn the dial toward isolation and you get merge hell when the branches eventually meet. Turn it toward integration and you need automated quality gates to catch breakage before it hits shared state. The best strategy is the one that matches your team's deployment frequency and test coverage.

What

A branching strategy defines: which branches are long-lived, when you branch (feature start? release start?), how you integrate (merge commit, squash, or rebase?), and who can merge where. It is the social protocol for a team sharing a codebase.

Why it matters

The wrong branching strategy is a leading cause of "integration hell" — days before a release merging months of parallel work. It is also a leading cause of slow feedback loops — feature branches that live for weeks mean engineers work in isolation and only find conflicts at merge time, not when they're introduced.

How — The Three Common Strategies

Trunk-Based Development: All commits go directly to main (or via branches that live <1 day). Incomplete features are hidden by feature flags. Requires: strong test coverage, feature flag infrastructure, senior discipline. Used by: Google, Facebook, Netflix.

GitHub Flow: Short-lived feature branches → PR → squash merge to main → auto-deploy. main is always deployable. No release branches. Requires: CI that runs on every PR, ability to deploy frequently. Used by: GitHub, Shopify, Vercel.

GitFlow: main (stable releases) + develop (integration) + feature/* + release/* + hotfix/*. Multiple concurrent production versions. Requires: long release cycles, enterprise compliance. Used by: Enterprise software with LTS versions.

When to use each

Trunk-based: continuous delivery, 10+ deploys/day, feature flags available. GitHub Flow: daily deploys, one production version, small-medium teams. GitFlow: weekly/monthly releases, multiple supported versions (SaaS with enterprise customers on v2 while v3 ships), compliance-heavy industries.

🌍
Real-World: Shopify's Sub-10-Minute Deployment Pipeline

Shopify runs GitHub Flow on a Rails monolith. Their CI pipeline runs 10,000+ Ruby tests split across 20 parallel workers, completing in under 10 minutes. Feature flags (Flipper) gate all in-progress work, enabling trunk-based development at 350+ engineers without long-lived branches. Every merge to main is auto-deployed via their internal Shipit tool — not GitHub Actions — because they needed finer-grained control over their deployment sequence. Key lesson: the branching strategy (GitHub Flow) and the deployment tool (custom Shipit) are separate decisions; choosing the right tool for each is the senior architect's job.

⚠️
Gotcha — GitFlow on a continuous delivery team

GitFlow was designed for teams that release once a month with multiple supported versions. Using it for a team that deploys daily is an anti-pattern. The overhead of develop → release/* → main means every feature takes 3 extra branch operations and introduces 1-2 weeks of latency between code being written and code being in production. Engineers who write this code lose feedback fast. The symptom: "why did this bug reach prod? We wrote the fix 2 weeks ago." Answer: it was sitting in a release branch waiting for the next release window.

3 · The CI/CD Mental Model

🧠
Mental Model — The Quality Gate Assembly Line

A CI/CD pipeline is a quality gate assembly line. Each station checks a specific failure mode. If a check fails, the piece is rejected before reaching the next stage. A car doesn't reach the dealer with a broken engine because the engine test station rejected it first. Your pipeline's job is to catch defects at the cheapest possible stage — a linting error caught before review costs 10 seconds; the same defect found by a customer costs 10 hours.

What

CI (Continuous Integration) is the practice of automatically building and testing every code change. CD (Continuous Delivery/Deployment) extends it to automatically deploy to staging and/or production. Together, they eliminate the manual, error-prone steps between "code written" and "code in production."

Why it exists

Before CI/CD: build on my machine → manually run (some) tests → email the binary to ops → ops manually deploy → hope it works. Each manual step is a place where: (a) someone forgets a step, (b) environment differences cause surprises, (c) there's no audit trail. CI/CD makes the process deterministic, auditable, and fast.

How — The Gate Structure

A well-designed pipeline has gates in order of speed and cost:

  1. Gate 1 — Fast feedback (parallel): lint + unit tests + SAST (target: <3 min)
  2. Gate 2 — Build artifact: compile/package/containerise (target: <5 min)
  3. Gate 3 — Integration: integration tests + container scan (target: <10 min)
  4. Gate 4 — Staging: deploy to staging + smoke tests (target: <5 min)
  5. Gate 5 — Production: canary deploy + metric verification

Each gate runs only if the previous passed. Gates within a gate run in parallel.

When to add a gate

When you've been burned by that class of failure reaching production more than twice. The gate should be fast enough that the team doesn't disable it. A gate that slows the pipeline by 30 minutes for marginal benefit will be bypassed by engineers under deadline. Every gate is a trade-off between safety and speed — name it explicitly.

DORA Metrics — The Four Numbers That Define Pipeline Health

Google's DevOps Research and Assessment (DORA) team identified the four metrics that most accurately predict software delivery performance and organisational performance. Your pipeline is the primary lever for all four:

MetricEliteHighMediumLow
Deployment frequencyMultiple/dayWeeklyMonthly>6 months
Lead time for changes<1 hour1 day–1 week1–6 months>6 months
Change failure rate0–5%5–10%10–15%>15%
Time to restore service<1 hour<1 day1 day–1 week>1 week
🔎
Fast pipelines improve all four DORA metrics

A 45-minute pipeline causes engineers to batch changes (larger PRs → higher blast radius → higher change failure rate). It also means test failures are discovered 45 minutes after the defect was introduced (long lead time → cold context switching). A 5-minute pipeline enables small, frequent changes: low deployment frequency barrier → more deploys → lower blast radius per deploy → lower failure rate → faster restoration when things go wrong. Pipeline speed is not a vanity metric — it's a force multiplier on every DORA metric.

4 · GitHub Actions Architecture

🧠
Mental Model — The Event-Driven Workflow Engine

GitHub Actions is an event broker built into your source control. An event (push to main, PR opened, schedule, manual trigger) is published. Your workflow YAML is the event handler — it declares which events to react to and what to do. Jobs are the parallel processing units; steps are the sequential operations within a job. The key insight: the workflow YAML is code — version-controlled, reviewable, testable. Treat it with the same rigor as application code.

What

GitHub Actions is an event-driven automation platform built into GitHub. A workflow is a YAML file in .github/workflows/ that defines: which events trigger it, which jobs to run (on which runner), and which steps to execute in each job. A runner is the VM or container where steps execute. An action is a reusable step packaged as Docker container or JavaScript.

Why GitHub Actions over alternatives

For teams already on GitHub: zero infrastructure to maintain, native PR integration (required status checks, deployment environments), a marketplace of 20,000+ actions, and OIDC for passwordless cloud authentication. The operational cost is zero for public repos and modest for private repos. The alternative (Jenkins) requires a dedicated server, plugin management, and engineering time to maintain — costs justified only when on-premises builds are required.

How — The Component Hierarchy

From outermost to innermost:

Repository → Workflows
One repo can have many workflow files, each for a different purpose (CI, CD, security scans, scheduled tasks).
Workflow → Trigger + Jobs
Trigger: when this workflow activates. Jobs: the units of work (run in parallel by default).
Job → Runner + Steps
Runner: the VM type (ubuntu-latest, windows-latest, self-hosted). Steps: sequential commands within a job.
Step → Action or shell command
Either uses: actions/checkout@v4 (invokes a packaged action) or run: pytest tests/ (shell command).
When to use which runner

GitHub-hosted (ubuntu-latest): 95% of cases — no maintenance, ephemeral, already has Docker and major language runtimes. Self-hosted: when you need private network access (RDS in a VPC), specific hardware (GPU for ML tests), regulatory compliance (code must not leave your network), or persistent build caches.

# ✅ PRODUCTION-GRADE WORKFLOW — every decision explained
name: CI/CD Pipeline

on:
  push:
    branches: [main]
    paths:                          # ✓ only run when code changes
      - 'src/**'
      - 'tests/**'
      - 'requirements*.txt'
  pull_request:
    branches: [main]
    types: [opened, synchronize, reopened]

# ✓ cancel stale runs; queue prod deploys (never cancel them)
concurrency:
  group: ${{ github.workflow }}-${{ github.ref }}
  cancel-in-progress: ${{ github.ref != 'refs/heads/main' }}

jobs:
  # ── GATE 1: parallel, fast (target: under 3 minutes) ──────────
  lint:
    runs-on: ubuntu-latest
    timeout-minutes: 5             # ✓ never hang
    steps:
      - uses: actions/checkout@v4  # ✓ pinned to major version
      - uses: actions/setup-python@v5
        with: { python-version: '3.11', cache: pip }  # ✓ cache deps
      - run: pip install ruff && ruff check . && ruff format --check .

  unit-tests:
    runs-on: ubuntu-latest
    timeout-minutes: 10
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-python@v5
        with: { python-version: '3.11', cache: pip }
      - run: pip install -r requirements-dev.txt
      - run: pytest tests/unit/ --tb=short --cov=src --cov-report=xml

  security-scan:
    runs-on: ubuntu-latest
    timeout-minutes: 8
    steps:
      - uses: actions/checkout@v4
      - uses: pypa/gh-action-pip-audit@v1.1.0  # ✓ CVE scan
      - uses: returntocorp/semgrep-action@v1    # ✓ SAST

  # ── GATE 2: build (waits for ALL of Gate 1) ────────────────────
  build:
    needs: [lint, unit-tests, security-scan]  # ✓ all gates must pass
    runs-on: ubuntu-latest
    timeout-minutes: 20
    permissions:
      contents: read
      packages: write
      id-token: write  # ✓ OIDC — no stored credentials
    outputs:
      image-tag: ${{ steps.meta.outputs.tags }}
    steps:
      - uses: actions/checkout@v4
      - uses: docker/setup-buildx-action@v3
      - uses: docker/login-action@v3
        with: { registry: ghcr.io, username: ${{ github.actor }},
                 password: ${{ secrets.GITHUB_TOKEN }} }
      - id: meta
        uses: docker/metadata-action@v5
        with: { images: ghcr.io/${{ github.repository }},
                 tags: "type=sha,prefix=sha-" }
      - uses: docker/build-push-action@v6
        with: { push: ${{ github.event_name != 'pull_request' }},
                 tags: ${{ steps.meta.outputs.tags }},
                 cache-from: type=gha, cache-to: type=gha,mode=max }
✅
Five non-negotiable workflow properties
  • Timeout on every job — a job without timeout-minutes can run indefinitely and block runner minutes
  • Dependency caching — actions/setup-python@v5 with cache: pip reduces install time from 60s to 3s
  • Pinned actions — @v4 not @main (supply chain protection)
  • Concurrency groups — prevents two deploys racing; cancels stale PR runs
  • Path filters — only run CI on relevant changes (docs change ≠ run all tests)

5 · Secrets & OIDC Security

🧠
Mental Model — Eliminate the Credential, Not Just Rotate It

The goal is not to store a long-lived AWS key securely. The goal is to not have a long-lived AWS key at all. OIDC achieves this: GitHub proves its identity to AWS, AWS issues a credential that expires when the job ends. There is no secret to store, no rotation schedule, and no blast radius if something leaks — an expired credential is useless. This is the zero-trust architecture applied to CI/CD.

What — OIDC

OpenID Connect (OIDC) is an identity protocol. GitHub issues a short-lived signed JWT (JSON Web Token) to each running job. Your cloud provider (AWS, GCP, Azure) is configured to trust GitHub's OIDC issuer. The job presents the JWT to the cloud provider's STS endpoint. STS verifies the signature and the claims (which repo, which branch, which environment), then issues a short-lived credential. The credential expires when the job ends.

Why OIDC over stored secrets

Stored secrets have three failure modes: they can be committed accidentally, leaked from GitHub's systems, or persisted after the person who created them leaves. OIDC eliminates the secret entirely. No rotation needed. A stolen OIDC JWT is useless after the job ends (typically <15 minutes). AWS CloudTrail shows exactly which GitHub repo and workflow made which API calls — a complete audit trail without any credential management overhead.

How — The Token Flow
  1. Job starts → GitHub's OIDC provider issues a signed JWT with claims: sub: repo:org/repo:ref:refs/heads/main
  2. Workflow calls aws-actions/configure-aws-credentials with the role ARN
  3. Action presents JWT to AWS STS AssumeRoleWithWebIdentity
  4. AWS verifies JWT signature against GitHub's public JWKS endpoint
  5. AWS checks the IAM role's trust policy: does the JWT's sub match the allowed repos?
  6. AWS issues temporary credentials (15min–12hr TTL)
  7. Job uses credentials → they expire automatically when the job ends
When to use OIDC vs stored secrets

Use OIDC for all cloud provider authentication where the provider supports it (AWS, GCP, Azure, Vault all support OIDC from GitHub Actions). Use stored GitHub Secrets for: third-party SaaS tokens that don't support OIDC (Datadog, PagerDuty, Slack), or when you need a specific credential format. OIDC for cloud is the industry standard as of 2024.

🚨
The Codecov Supply-Chain Attack (2021) — a real incident

Attackers compromised Codecov's bash uploader script. Teams using curl -s https://codecov.io/bash | bash in their CI pipelines had environment variables (including $CODECOV_TOKEN) exfiltrated to the attacker. Affected organisations included Twitch, Twilio, HashiCorp, and Rapid7. What should have prevented it: (1) Use the official GitHub Action (codecov/codecov-action) which is code-reviewed and signed; (2) Never pipe remote scripts to bash; (3) Pin the action to a SHA: codecov/codecov-action@f9ed4c.... This incident is the canonical argument for pinning actions to commit SHAs rather than version tags.

6 · Advanced Workflow Patterns

What — Reusable Workflows

A reusable workflow is a full workflow file that can be called by other workflows via uses: ./.github/workflows/_deploy.yml. It has defined inputs and can receive secrets from the caller. Unlike composite actions (which are step-level reuse), reusable workflows provide job-level reuse with their own runners — enabling a platform team to maintain one deploy workflow used by 50 services.

Why reusable workflows

Without reusable workflows, each of 50 microservices has a copy of the same CI logic. When you need to add a security scan step, you update 50 YAML files. With a reusable workflow, the platform team updates one file and all 50 services inherit the change on their next run. DRY applied to pipeline code.

# .github/workflows/_python-service.yml — the reusable template
on:
  workflow_call:
    inputs:
      service-name: { type: string, required: true }
      environment:  { type: string, default: staging }
    secrets:
      KUBE_CONFIG: { required: true }

jobs:
  ci:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-python@v5
        with: { python-version: '3.11', cache: pip }
      - run: pip install -r requirements-dev.txt && pytest tests/
      - run: docker build -t ${{ inputs.service-name }}:${{ github.sha }} .

# ── Each service's Jenkinsfile becomes two lines ──────────────
# services/payment-service/.github/workflows/ci.yml
on: { push: { branches: [main] } }
jobs:
  pipeline:
    uses: ./.github/workflows/_python-service.yml
    with: { service-name: payment-service, environment: production }
    secrets: inherit  # pass all secrets to reusable workflow

Matrix Builds — Test Across Versions Simultaneously

# Test across Python 3.9, 3.10, 3.11, 3.12 AND Linux + Windows simultaneously
jobs:
  test:
    strategy:
      fail-fast: false  # ✓ run all matrix combos even if one fails
      matrix:
        python-version: ["3.9", "3.10", "3.11", "3.12"]
        os: [ubuntu-latest, windows-latest]
        exclude:  # optional: skip specific combinations
          - { os: windows-latest, python-version: "3.9" }
    runs-on: ${{ matrix.os }}
    steps:
      - uses: actions/setup-python@v5
        with: { python-version: ${{ matrix.python-version }} }
      - run: pytest tests/
# Spawns 7 jobs simultaneously (4 python × 2 os, minus 1 exclusion)

7 · Monorepo vs Polyrepo CI

🧠
Mental Model — Conway's Law and Repo Structure

Conway's Law: organisations build systems that mirror their communication structure. A polyrepo enforces team autonomy — each team owns their entire stack, deploys independently, and rarely sees each other's code. A monorepo enforces cross-team visibility — changes to shared libraries are immediately visible to all consumers, refactors can span the entire codebase in one PR. Your repo structure is your org structure — choose deliberately.

DimensionMonorepoPolyrepo
Code sharingTrivial (same import path)Requires publishing packages with versions
Atomic cross-service changesOne PR changes 5 services5 PRs + coordination
CI scopeMust be path-filtered (changed services only)Each repo runs its own full suite
Team autonomyLower (shared ownership)Higher (each team owns their repo)
Build tooling complexityRequires Nx / Turborepo / BazelStandard tools
DiscoveryEverything in one placeNeed to know where to look
🌍
Real-World: Google's Monorepo at Extreme Scale

Google's Piper monorepo contains 2+ billion lines of code across every product. Their custom CI system (TAP — Test Automation Platform) runs tests for every file that transitively depends on changed code — using Bazel's hermetic, reproducible build graph to determine affected targets. A change to a core library automatically tests all 10,000 services that depend on it. The key infrastructure: Bazel's hermetic builds (same binary on any machine, anywhere), distributed build caching (no redundant compilation), and CODE_OWNER files that route reviews to the right team. Without this tooling, a monorepo at this scale would be unusable. The lesson: monorepo is a strategy that requires investment in tooling; polyrepo is a strategy that requires investment in package management and versioning.

8 · Real-World Case Studies

Netflix — Freedom and Responsibility at CI Scale

Netflix runs 2,000+ microservices with 500+ engineers deploying multiple times per hour. Their CI/CD philosophy is "freedom and responsibility": each service team owns their entire pipeline, with no central CI team gate-keeping deployments.

  • Spinnaker (open-sourced by Netflix): pipeline orchestration platform that manages canary deployments, automated rollback, and multi-cloud deployments.
  • Canary analysis: every deployment starts at 1% traffic, with automated comparison of error rate, latency, and business metrics against the baseline. Auto-promote or auto-rollback based on statistical significance.
  • Chaos Engineering: CI pipelines include chaos tests (Chaos Monkey) — services must pass resiliency tests before deployment.

Key architectural decision: Netflix chose service team autonomy over centralised control. This means each team can deploy independently without coordinating with others — maximising deployment frequency — but also means there's no central safety net. Each team is responsible for their own reliability.

GitHub — Self-Hosting GitHub Actions

GitHub uses GitHub Actions to build and deploy GitHub itself. They run their own self-hosted runners for compliance-sensitive deployments. Their CI pipeline for github.com includes:

  • Tens of thousands of tests across Ruby, TypeScript, Go, and Rust
  • Rolling deployments to hundreds of servers using their internal deployment system
  • Feature flags (Flipper) for gradual rollouts to 100M+ users
  • Blue/green deployments for infrastructure changes

9 · The Pipeline Design Framework

🧠
The 7 Questions Before Any Pipeline

A senior architect doesn't start writing YAML. They answer seven questions first:

  1. Deployment target: Where does the artifact go? (K8s, ECS, serverless, VMs)
  2. Artifact type: Docker image? JAR? ZIP? Python wheel? (determines the build stage)
  3. Quality gates: What must be true before production? (determines gates)
  4. Secrets: What credentials does the pipeline need? Can OIDC eliminate them?
  5. Speed target: What feedback time is acceptable for a PR? (drives parallelism design)
  6. Failure handling: Auto-rollback on metric degradation? Manual approval for prod?
  7. Maintenance: Who owns this pipeline? Is it DRY (reusable workflow) or duplicated?

Chapter Takeaways
  • Git is a content-addressed DAG — immutability and deduplication are emergent properties, not features
  • Branch strategy = blast-radius dial; match it to your deployment frequency and team size
  • CI/CD pipeline = quality gate assembly line; gates run in order of speed and cost
  • DORA metrics are the measurable outcome; pipeline speed is the input
  • OIDC eliminates long-lived credentials — aim for zero stored cloud credentials in CI
  • Reusable workflows are DRY applied to pipeline code — one change propagates to all services
