Docker — From Kernel Primitives to Production Containers
The artifact that connects your CI pipeline to your Kubernetes cluster
📦

A container is not a mini-VM. It is a Linux process (or group of processes) with an isolated view of the OS, enforced by two kernel primitives: namespaces (isolation) and cgroups (resource limits). Understanding this foundation explains every Docker behaviour — why containers start in milliseconds, why they share the host kernel's attack surface, and why multi-stage builds produce binaries instead of entire OS installations.

1 · Containers vs VMs — Linux Primitives

🧠
Mental Model — Walled Gardens vs Separate Houses

A VM is a separate house with its own foundation (kernel), walls (OS), and utilities. A container is a walled garden on the same property: same foundation (host kernel), separate garden (isolated process view). The garden is much cheaper to build and can be planted/removed instantly. But if the foundation has a problem, it can affect all gardens. VMs provide stronger isolation; containers provide faster, denser packing.

What

A container is a process tree running in a set of Linux namespaces with resource constraints enforced by cgroups. There is no separate kernel — the container shares the host kernel. A VM, by contrast, runs a complete guest OS on top of a hypervisor, which emulates hardware. The fundamental difference is: containers share the kernel; VMs have their own.

Why containers over VMs (for most workloads)

Startup time: milliseconds (process spawn) vs 30–60 seconds (OS boot). Density: 100s of containers per host vs 10s of VMs. Image size: megabytes vs gigabytes. Resource overhead: near-zero (no hypervisor) vs significant (guest OS RAM and CPU). For workloads requiring strict multi-tenant security isolation (e.g., running untrusted third-party code), VMs remain the right choice.

How — Linux Primitives Explained
pid namespace
Container has its own PID 1. Processes inside cannot see host PIDs or other containers' PIDs.
net namespace
Container has its own network stack, IP address, port space. Port 8080 in the container ≠ port 8080 on the host.
mnt namespace
Container sees a different filesystem tree. The host's /etc is hidden; the container's /etc is from its image.
uts namespace
Container has its own hostname.
user namespace
Container UID 0 (root) maps to a non-root UID on the host. The foundation of rootless containers.
cgroups (v2)
Enforces resource limits: CPU (millicores), memory (bytes), block I/O, network bandwidth. If a container exceeds its memory cgroup limit — it's OOMKilled.
When containers are NOT enough

Multi-tenant SaaS where tenants run arbitrary code (cloud functions as a service): use VMs (Firecracker microVMs) or gVisor for kernel-level isolation. Containers are appropriate for trusted workloads (your own application code) but not for untrusted code where a kernel exploit could break isolation. AWS Fargate uses Firecracker to give each task its own kernel — the cloud knows this distinction.

🌍
Real-World: AWS Fargate — Containers with VM-level Isolation

AWS Fargate gives each container task its own kernel using Firecracker microVMs — 125ms boot time, ~5MB memory overhead per microVM, full kernel isolation. This is how AWS runs multi-tenant container workloads safely: containers for density and speed, a separate kernel for isolation. If you are running containers for multiple tenants who could potentially exploit your application, use Fargate or a similar hardened runtime — not plain Docker on a shared kernel.

3 · Image Layers — The Union Filesystem

🧠
Mental Model — A Stack of Transparent Slides

A Docker image is a stack of read-only layers, like stacking transparent slides. Each layer adds or modifies content. When you read a file, Docker looks down through the stack until it finds it. When you write a file in a running container, the write goes to a new writable layer at the top (copy-on-write). The genius: identical layers are shared. Ten containers running nginx:1.25 share a single copy of the nginx layer in memory and on disk — not ten copies.

What

An image is a sequence of immutable, content-addressed layers stored as tar archives. The container runtime assembles them into a unified filesystem view using OverlayFS (the default driver on modern Linux). Each layer is identified by a digest (SHA-256 of its content). The same digest = the same layer = deduplicated storage across all images and all containers on the host.

How — Cache Invalidation Rule

Docker rebuilds a layer when its content changes. Since each layer builds on the previous, if any layer changes, all layers below it must rebuild. This is the single most important rule for Dockerfile optimisation:

# ❌ SLOW: code change → pip install runs every time (90 seconds!)
FROM python:3.11-slim
COPY . /app              # ← copies ALL files first
RUN pip install -r /app/requirements.txt  # ← ALWAYS rebuilds

# ✅ FAST: code change → only COPY layer rebuilds (2 seconds!)
FROM python:3.11-slim
COPY requirements.txt /app/  # ← only lockfile (rarely changes)
RUN pip install -r /app/requirements.txt  # ← cached unless req changes
COPY . /app              # ← code last (frequent changes)

Rule: most-stable instruction → top. most-frequently changing → bottom.

4 · Dockerfile Deep Dive

What

A Dockerfile is a recipe for building a Docker image. Each instruction (FROM, RUN, COPY, CMD) creates a layer. The Dockerfile is the source of truth for the deployment artifact — treat it like application code: review it, lint it (Hadolint), and audit it for security.

# ✅ PRODUCTION DOCKERFILE — Python service, every decision explained

# ── Stage 1: Builder ────────────────────────────────────────────
FROM python:3.11.9-slim-bookworm AS builder   # ✓ exact version, slim = smaller
WORKDIR /build

# ✓ Install build tools in builder only — they never reach the final image
RUN apt-get update && apt-get install -y --no-install-recommends \
    gcc libpq-dev \
    && rm -rf /var/lib/apt/lists/*   # ✓ clean cache IN SAME LAYER

COPY requirements.txt .             # ✓ lockfile first (stable layer)
RUN pip install --prefix=/install --no-cache-dir -r requirements.txt

# ── Stage 2: Runtime ────────────────────────────────────────────
FROM python:3.11.9-slim-bookworm AS runtime   # ✓ same base, no build tools

# ✓ Non-root user — CRITICAL for security
RUN groupadd --gid 1001 appuser && \
    useradd --uid 1001 --gid appuser --shell /bin/bash --create-home appuser

WORKDIR /app

# ✓ Copy only compiled packages from builder — not gcc, not build tools
COPY --from=builder /install /usr/local
COPY --chown=appuser:appuser src/ ./src/
COPY --chown=appuser:appuser main.py .

USER appuser   # ✓ switch to non-root BEFORE CMD

# ✓ Health check — used by Docker and Kubernetes readiness
HEALTHCHECK --interval=30s --timeout=5s --start-period=10s --retries=3 \
    CMD python -c "import urllib.request; urllib.request.urlopen('http://localhost:8000/health')"

EXPOSE 8000   # ✓ documentation only — does not publish the port

# ✓ ENTRYPOINT = the command (protected); CMD = default args (overridable)
ENTRYPOINT ["python", "-m", "uvicorn"]
CMD ["main:app", "--host", "0.0.0.0", "--port", "8000"]

5 · Multi-Stage Builds — Ship Only the Product

🧠
Mental Model — The Factory Floor vs the Product

You don't ship the factory floor to the customer — you ship the product. Multi-stage builds apply this to containers: Stage 1 is the factory (compiler, build tools, test runner). Stage 2 is the product (compiled binary or optimised artifact). Only Stage 2 reaches production. No compiler in production = 80% smaller image, no compiler in CVE scans, no development tools in the attack surface.

LanguageSingle-stage sizeMulti-stage sizeReduction
Go binary~800 MB (Go toolchain)5–30 MB (scratch + binary)30–160×
Java Spring Boot~800 MB (JDK + sources)~150 MB (JRE + JAR)5×
Python API~800 MB (with gcc)~200 MB (slim + app)4×
Rust binary~2 GB (Rust toolchain)5–50 MB (scratch + binary)40–400×
Node.js API~1.2 GB (with devDeps)~150 MB (prod deps only)8×
🔎
Why image size matters in production economics

A team of 50 engineers pushing 20 images per day: 800 MB × 1,000 pulls/day = 800 GB/day of registry traffic. At $0.09/GB (AWS ECR egress): $72/day = $26,280/year. Optimise to 150 MB: $4,935/year. Savings: $21,345/year — just from multi-stage builds. But cost is secondary to speed: pulling a 150 MB image takes 2 seconds; pulling 800 MB takes 15 seconds. At 10 deploys/day × 100 pods per deployment, that 13-second difference matters for autoscaler response time.

6 · Security Hardening

How — Defence in Depth

Container security is a layered defence. Each layer reduces the attacker's options if the application is compromised:

  1. Non-root user: USER 1001 — even with code execution, can't write to system directories
  2. Read-only root filesystem: docker run --read-only / K8s readOnlyRootFilesystem: true — can't install tools or modify binary
  3. Drop all capabilities: --cap-drop ALL — can't bind port <1024, can't modify kernel params
  4. No new privileges: --security-opt no-new-privileges — can't escalate via setuid binaries
  5. Seccomp profile: limits which syscalls the process can make (Docker default profile blocks ~44 syscalls)
  6. Image scanning: trivy image myapp:latest in CI — catch CVEs before they reach production
🌍
Real-World: OpenShift — Non-Root by Default Since 2014

Red Hat OpenShift has required all containers to run as non-root since its first release. Any image that requires root — including official images like nginx:latest — will fail to start on OpenShift. This forced the ecosystem to create hardened alternatives (bitnami/nginx runs as UID 1001). The result: 10 years of OpenShift usage means RedHat customers have a decade of non-root container experience that dramatically reduces their container escape attack surface. Google GKE Autopilot adopted the same policy in 2021 — the industry has converged on non-root as the default.

8 · Docker in CI/CD

What — BuildKit

BuildKit is the modern Docker build engine (enabled by default since Docker 23). Key features for CI: parallel stage execution in multi-stage builds, better layer caching, cache mounts (--mount=type=cache for pip/npm caches that persist across builds), and build secrets (--secret id=key,env=API_KEY — the secret is never written to a layer).

# ✅ BuildKit in GitHub Actions: layer cache via registry
- uses: docker/build-push-action@v6
  with:
    context: .
    push: ${{ github.event_name != 'pull_request' }}
    tags: ghcr.io/${{ github.repository }}:sha-${{ github.sha }}
    # ✓ Cache layers in GitHub Actions cache (free, fast)
    cache-from: type=gha
    cache-to:   type=gha,mode=max
    # ✓ Build secret — never written to a layer
    secrets: |
      GIT_AUTH_TOKEN=${{ secrets.GIT_AUTH_TOKEN }}
✅
Chapter Takeaways
  • A container is a process with namespaces + cgroups — not a VM. It shares the host kernel.
  • Layer order matters: most stable instruction first, most frequently changed last
  • Multi-stage builds are not optional for production — they reduce size, CVEs, and cost
  • Non-root user is non-negotiable — every production container runs as UID > 0
  • Pin base image to a specific version SHA, not latest
  • Scan images in CI with trivy or grype — catch CVEs before production
  • BuildKit layer caching in CI reduces Docker build time from 5 minutes to 30 seconds
