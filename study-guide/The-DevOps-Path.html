The Senior DevOps Architect's Mental Stack
How the seven tools connect into one coherent system — and the 10 questions that define the architectural mindset
🏗️

A junior engineer asks "how do I deploy this container?" A senior DevOps architect asks "how do I design a system where any engineer can deploy a container safely, repeatedly, with full observability, in under 10 minutes, with automatic rollback if something goes wrong?" The difference is not more syntax knowledge — it is systems thinking: understanding how tools compose into a platform.

The DevOps Lifecycle — How the Tools Connect

🧠
Mental Model — The Factory Assembly Line

DevOps is an assembly line, not a collection of independent tools. Code enters at one end (Git), passes through quality gates (CI/CD), gets packaged (Docker), runs at scale (Kubernetes), with its infrastructure provisioned below (Terraform, Ansible) and observability layered above (Prometheus, ELK). Each tool is a station on the line. Remove any station and the product reaches the customer in a worse state. The senior architect's job is to design the line so that each station's output is the next station's input — seamlessly, automatically, and safely.

The 10 Commandments of a DevOps Architect

💡
The principles that separate architects from operators
  1. Everything is code. Infrastructure, config, pipelines, runbooks — if it isn't in Git, it doesn't exist.
  2. Automate the blast radius. If a human must remember a step, it will be forgotten. Automate every step between code and production.
  3. Design for failure. Every component will fail. Design so the system doesn't. Chaos Engineering proves it.
  4. Immutable over mutable. Rebuild containers and VMs rather than patching in place. Immutable infrastructure is reproducible infrastructure.
  5. Fast feedback loops. A 45-minute pipeline is a slow compiler — engineers stop fixing tests. Target <10 minutes CI to production signal.
  6. Least privilege everywhere. The container, the pipeline, the service account, the IAM role. No credential should outlive the job that needs it.
  7. Observable from day one. Metrics, logs, and traces are not added later — they are the design. Instrument as you build.
  8. The deployment is not the end. Rollback, canary, and runbook are part of the feature. Define them before you deploy.
  9. Blast radius before blast-off. For every change: how bad can it get? Can you limit it? Can you recover automatically? If the answer to all three is "no", you're not ready to deploy.
  10. Document the why, not the what. Code and YAML show the what. Architecture notes show why. The why is what transfers between engineers.

The Interview Gauntlet — 10 Senior-Level Questions

1. Design a CI/CD pipeline for a Python microservice that deploys to Kubernetes. The team deploys 10+ times per day. What does the full pipeline look like?

Gate 1 (parallel, <3min): lint + unit tests + SAST. Gate 2: Docker multi-stage build (BuildKit layer cache) + image scan (trivy). Gate 3: push to ECR, deploy to staging via Helm + smoke tests. Gate 4: canary deploy to prod (Argo Rollouts: 5% → 15min → 50% → 100%) with automated Prometheus metric gates. OIDC for all AWS auth. Concurrency groups to prevent deploy races. Reusable workflow shared across all 20 microservices.

2. A production deployment is causing a high error rate. Describe your response from the moment you get paged.

Acknowledge alert. Check dashboard: which service, what error rate, since when. Compare timing to deployment events — did a deploy just happen? If yes: rollback immediately (kubectl rollout undo or Argo Rollouts auto-rollback). If no: check logs for error pattern, find a trace_id, trace the request to find the bottleneck. Mitigate first (rollback, feature flag off, circuit breaker). Root cause during business hours. Post-mortem within 48 hours.

3. A Terraform apply destroyed a production RDS database. What should have prevented this?

Three prevention layers: (1) prevent_destroy = true lifecycle rule on the RDS resource — Terraform refuses to destroy it and fails the plan. (2) Atlantis workflow — the plan showing a database destruction would have been visible in the PR for review. (3) AWS Service Control Policy preventing database deletion from the Terraform role. Recovery: restore from automated RDS snapshot. Post-mortem: add all three layers.

4. How do you handle secrets in a GitHub Actions pipeline that needs to push to ECR?

OIDC. Configure GitHub as a trusted OIDC identity provider in AWS IAM. Create an IAM role with ECR push permissions and a trust policy restricting to your GitHub repo/branch. In the workflow: permissions: id-token: write + aws-actions/configure-aws-credentials with the role ARN. No AWS keys stored anywhere. Credentials expire when the job ends.

5. What is the difference between Ansible and Terraform? Give a concrete example of where each is used.

Terraform provisions cloud infrastructure via APIs (creates EC2 instances, VPCs, RDS databases, load balancers). Ansible configures what runs inside that infrastructure via SSH (installs nginx, copies config templates, creates OS users, runs database migrations). Canonical workflow: Terraform creates the EC2 instance, outputs its IP, Ansible connects and configures it. They are complementary. Don't use Terraform for OS-level config; don't use Ansible to create VPCs.

Master Overview Takeaways
  • DevOps is a system: Git → Pipeline → Docker → Kubernetes, with Ansible/Terraform below and Monitoring above
  • The difference between junior and senior is systems thinking: understanding how each tool affects every other tool
  • Every decision has a trade-off. Name it. That is what separates architects from operators.
  • The 10 Commandments are the principles; the seven books are the implementation
  • Study one book per week. Run the code. Break it intentionally. Answer the interview questions from memory.
