Kubernetes — The Desired-State Orchestrator
Tell it WHAT you want, and it continuously works to make the cluster match your declaration
🔄

Kubernetes is not a deployment tool. It is a desired-state reconciliation engine. You declare what you want — "3 replicas of this container image" — and Kubernetes continuously monitors the cluster and takes actions to match that declaration. If a node fails, it reschedules. If a pod crashes, it restarts. If you change the desired replicas to 5, it starts 2 more. You never tell Kubernetes how to do anything — you tell it what you want.

1 · The Desired-State Mental Model

🧠
Mental Model — The Thermostat

A thermostat is a desired-state controller. You set the desired temperature (22°C). The thermostat observes the actual temperature. If actual < desired: turn on heat. If actual > desired: turn on cooling. It runs this loop forever, autonomously, without you telling it to "please heat the room now." Kubernetes works the same way: desired state in YAML, actual state in the cluster, reconciliation loop running every few seconds.

How — The Reconciliation Loop (in pseudocode) 
# Every Kubernetes controller implements this exact pattern
while True:
    desired = read_from_api_server()   # what you declared in YAML
    actual  = observe_the_cluster()    # what's actually running

    if desired != actual:
        reconcile(desired, actual)     # create/update/delete resources

    sleep(reconcile_interval)          # typically 5-30 seconds

Every built-in Kubernetes resource has a controller implementing this loop: ReplicaSet controller (maintains pod count), Deployment controller (manages ReplicaSets for rolling updates), Endpoints controller (keeps Service backends current), Node controller (evicts pods from failed nodes), HPA controller (scales Deployments on metrics).

🌍
Real-World: Dropbox — Self-Healing at 2 AM

A hardware failure took down an entire rack at Dropbox at 2 AM. No engineer woke up. Kubernetes detected node failures via missed heartbeats (default: 5 minutes), marked nodes NotReady, and rescheduled all affected pods to healthy nodes — automatically, in under 3 minutes. The on-call engineer acknowledged the alert, confirmed the system had recovered, and created a ticket for hardware replacement. Total engineer time: 5 minutes. Without Kubernetes: SSH into each server, manually restart services, update load balancer configs, verify each service — 45-minute incident at 2 AM.

2 · Control Plane vs Data Plane

🚨
etcd is the single most critical component — treat it accordingly

etcd stores every Kubernetes object, every RBAC rule, every secret. If etcd is lost and you have no backup: your cluster is effectively gone. Running pods keep running (kubelet doesn't need etcd for already-running pods), but no new scheduling can happen, no healing, no config changes. Production requirements: (1) etcd cluster of 3 or 5 nodes (odd for quorum), (2) SSD storage (etcd is I/O-sensitive — HDD = leader election failures under load), (3) automated backups with etcdctl snapshot save every 15 minutes to an offsite location, (4) separate nodes from worker nodes (noisy neighbours crash etcd). EKS/GKE/AKS handle etcd for you — a strong argument for managed K8s.

4 · Health Probes — The Most Misused Feature

🧠
Mental Model — Three Different Doctors

Three doctors check your health for different purposes. The startup doctor checks if you're awake after surgery — don't move you until you're conscious. The readiness doctor clears you to receive visitors — your room is only listed as available when you can actually host guests. The liveness doctor checks if you're responsive — if you're unresponsive, call a code. Each has a different response to failure.

ProbeQuestionOn failureCommon mistake
startupProbeIs the app done starting?Keep waiting (up to failureThreshold × period)Not setting it — liveness kills slow-starting apps
readinessProbeReady to receive traffic?Remove from Service endpoints (no traffic)Checking DB connectivity — DB outage takes all pods unready simultaneously
livenessProbeIs the app stuck/deadlocked?Kill and restart the podSame as readiness — all pods restart simultaneously on DB outage = cascading failure
# ✅ CORRECT: three probes, each doing exactly its job
startupProbe:          # ← waits for slow-starting JVM app (up to 5min)
  httpGet: { path: /health, port: 8080 }
  failureThreshold: 30
  periodSeconds: 10      # 30 × 10s = 5 minutes max startup window

readinessProbe:        # ← traffic control (DB check OK here)
  httpGet: { path: /ready, port: 8080 }
  initialDelaySeconds: 5
  periodSeconds: 10
  failureThreshold: 3

livenessProbe:         # ← deadlock detection ONLY (NO DB check!)
  httpGet: { path: /health, port: 8080 }
  initialDelaySeconds: 60  # longer than startupProbe max
  periodSeconds: 20
  failureThreshold: 3

8 · Deployment Strategies

What — Rolling Update

Kubernetes default. Replace pods one by one (or in batches) with the new version. maxUnavailable pods can be down at once; maxSurge extra pods can run above desired count. The pipeline: new pod starts → passes readiness probe → old pod removed. Zero-downtime if readiness is configured correctly.

What — Canary (Argo Rollouts)

Route a small percentage of traffic to the new version. Observe metrics (error rate, latency) for a defined period. If metrics are within bounds: promote to 100%. If metrics degrade: auto-rollback. Argo Rollouts integrates with Prometheus/Datadog for automated analysis gates. This is Netflix's default deployment model.

# Argo Rollouts canary with automated analysis
apiVersion: argoproj.io/v1alpha1
kind: Rollout
spec:
  strategy:
    canary:
      steps:
      - setWeight: 5       # 5% traffic to new version
      - pause: { duration: 10m }   # observe for 10 minutes
      - analysis:          # ← automated metric check
          templates: [{ templateName: success-rate }]
      - setWeight: 50      # 50% if analysis passed
      - pause: { duration: 5m }
      - setWeight: 100     # full rollout
✅
Chapter Takeaways
  • Kubernetes is a reconciliation engine — you declare desired state, it continuously makes it real
  • etcd is the most critical component — back it up, put it on SSDs, use managed K8s in production
  • readinessProbe controls traffic; livenessProbe controls restarts — NEVER check DB in livenessProbe
  • Resources requests and limits are required — BestEffort pods are evicted first under pressure
  • Services discover pods by label selectors — understand this to debug any networking issue
  • Canary deployments with automated metric gates (Argo Rollouts) are the elite deployment strategy
