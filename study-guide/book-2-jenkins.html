Jenkins — Enterprise CI/CD at Scale
The Controller-Agent architecture that powers pipelines in banks, aerospace, and healthcare
📜

Jenkins was created in 2004 (as Hudson) when CI/CD barely existed as a concept. Twenty years later, it remains the dominant CI system in regulated industries — not because it is the most modern tool, but because it is the most flexible, most self-hostable, and most extensible. Understanding Jenkins at the architectural level explains why large enterprises still choose it and how to use it well.

1 · Controller-Agent Architecture

🧠
Mental Model — The Factory Floor

Jenkins is a factory: the Controller (foreman) schedules work and assigns it to Agents (workers). Agents are the machines where code actually runs. The Controller should never run build jobs — it is the brain, not the muscle. A Controller running builds is like a foreman doing all the welding: the factory doesn't scale and the foreman is always the bottleneck.

What

The Jenkins Controller is the central server: it stores job configurations, build history, plugin state, and schedules work. Agents are machines (VMs, containers, physical servers) that the Controller connects to and dispatches build jobs. The Controller and agents communicate over JNLP, SSH, or WebSocket.

Why the separation matters

When a Controller runs builds directly: resource exhaustion causes the Controller to crash, and all CI stops — every team's pipeline is down simultaneously. By offloading work to agents, a Controller crash affects scheduling but not in-progress builds. Agents can also be specialised (docker-capable, GPU, Windows) and scaled independently.

2 · Declarative vs Scripted Pipelines

Scripted (Groovy) — maximum power, maximum complexity
// Full Groovy — can do anything, but harder to validate
node('python-build') {
  stage('Test') {
    try {
      sh 'pytest tests/'
    } catch (e) {
      currentBuild.result = 'FAILURE'
      throw e
    } finally {
      junit 'reports/*.xml'
    }
  }
}
Declarative — structured, validated, recommended
// Validated by Jenkins; safer and more readable
pipeline {
  agent { label 'python-build' }
  stages {
    stage('Test') {
      steps { sh 'pytest tests/' }
      post {
        always { junit 'reports/*.xml' }
      }
    }
  }
}

4 · Shared Libraries — Enterprise DRY

💡
The Pipeline-in-a-Function Pattern

The highest-leverage use of Shared Libraries is the pipeline-in-a-function pattern: the platform team writes a complete opinionated pipeline as a function in vars/. Each product team's Jenkinsfile calls that function with service-specific parameters. One function update propagates to all services. A product team's Jenkinsfile becomes three lines:

// Product team's entire Jenkinsfile:
@Library('company-lib@main') _
pythonMicroservicePipeline(
  serviceName: 'payment-service',
  requiresApproval: true,
  slackChannel: '#payments-deploys'
)
// vars/pythonMicroservicePipeline.groovy (platform team maintains this)
def call(Map config = [:]) {
  def name = config.serviceName ?: error('serviceName required')

  pipeline {
    agent { label 'python-build' }
    options {
      timeout(time: 30, unit: 'MINUTES')
      buildDiscarder(logRotator(numToKeepStr: '30'))
      disableConcurrentBuilds(abortPrevious: true)
    }
    stages {
      stage('Quality Gate') {
        parallel {
          stage('Lint')     { steps { runLint() } }
          stage('Tests')    { steps { runPytests(name) } }
          stage('Security') { steps { runSecurityScan() } }
        }
      }
      stage('Build')  { steps { buildDockerImage(name) } }
      stage('Deploy') {
        when { branch 'main' }
        steps { deployToK8s(name, config.requiresApproval) }
      }
    }
    post {
      failure { notifySlack(config.slackChannel, 'FAILED') }
      always  { cleanWs() }
    }
  }
}

🌍
Real-World: The Hybrid Model at a Global Bank

A top-5 global bank runs both Jenkins and GitHub Actions. Jenkins handles: core banking pipelines (builds must stay on-prem, compliance audit trail mandatory, HSM integration for signing), deployment to regulated environments (production approvals logged to immutable audit systems). GitHub Actions handles: developer tools, internal dashboards, documentation builds, open-source contributions. The architectural principle: use GitHub Actions where self-service speed matters; use Jenkins where compliance and on-premises control are non-negotiable. The two systems share the same Shared Library pattern — the bank maintains a GitHub Actions reusable workflow library with the same API as their Jenkins Shared Library, minimising cognitive switching cost for engineers who work on both sides.

Chapter Takeaways
  • Controller is the brain; agents are the muscles — never run builds on the Controller
  • Declarative pipelines by default; Scripted only for dynamic logic Declarative can't express
  • Shared Library + pipeline-in-a-function = DRY pipelines; platform team updates one file, all services benefit
  • Multi-branch pipelines auto-discover feature branches and PRs — no manual job creation
  • Vault integration eliminates long-lived Jenkins Credentials — dynamic, short-lived secrets per build
  • Jenkins wins on compliance, on-prem, and complex Groovy pipelines; Actions wins on simplicity and managed infra
