Branch Protection, CI Checks & GitHub Pages
Turning "we try to always run tests" into "it is technically impossible not to"
✅

A repository without branch protection is a repository where quality is a social contract. Social contracts fail under pressure. This book is about turning quality from a guideline into a technical constraint: a set of rules enforced by GitHub's API that make it physically impossible to merge code that hasn't passed every configured gate — regardless of who is merging, what time it is, or how much deadline pressure exists.

1 · The Enforcement Mindset

🧠
Mental Model — The Airlock

An airlock prevents vacuum from reaching the spacecraft cabin. It doesn't rely on astronauts remembering to close the inner door. The inner door cannot open while the outer door is open — it is mechanically prevented. Branch protection is the airlock for your codebase: the merge button cannot activate while required checks are failing, regardless of who presses it. No amount of time pressure, authority, or forgetting changes this fact.

Before — social contract

"We always run tests before merging."

Except at 2 AM during an incident. Except when the deadline is tomorrow. Except when a senior engineer with admin rights needs to "just quickly push this one thing."

Result: broken main branch every few months. Post-mortem: "we need to be more diligent."

After — technical enforcement

Branch protection rules + required status checks + CODEOWNERS.

At 2 AM, under deadline pressure, with the CTO watching: the merge button is still grey until all checks pass. The rules don't know who is merging. They don't care about the pressure.

Result: main branch has never been broken by a merged PR. Not by accident. Not by anyone.

2 · Branch Protection Rules

What

Branch protection rules are server-side constraints on a specific branch (usually main). They are enforced by GitHub's API — not by convention, not by pre-commit hooks, not by CI alone. Even git push --force from a machine with push access is blocked if the branch has force-push protection enabled.

Why

Because every other defence is bypassable. A pre-commit hook can be skipped with git commit --no-verify. CI can be ignored if the merge button still works when checks fail. Admin access can override everything. Branch protection rules with Include administrators are the only layer that has no escape hatch.

How — complete configuration for this repo

Navigate to: github.com/karthikb35/devops-study → Settings → Branches → Add rule

Branch name pattern: main

   Required approving reviews: 1
   ✅ Dismiss stale pull request approvals when new commits are pushed
   ✅ Require review from Code Owners
   ✅ Require approval of the most recent reviewable push

✅ Require status checks to pass before merging
   ✅ Require branches to be up to date before merging
   Required status checks (exact names):
     • Lint & Format (ruff)
     • Import Order (isort via ruff)

When to add each rule
Require PR (from day 1)
Even solo projects benefit — PRs create a record of every change, a trigger for CI, and a review checkpoint.
Include administrators (always)
Without this, any admin can bypass all rules. The rules exist for admins too — especially admins, who have the most access.
Linear history
When the git log is important for traceability (compliance, post-mortems). Not necessary for all teams, but valuable for regulated environments.

3 · Required Status Checks

🧠
Mental Model — The Named Contract

A required status check is a contract identified by an exact string (the check name). GitHub compares the check name against the names of CI jobs that ran on the PR's HEAD commit. The critical detail: the check name in GitHub branch protection settings must exactly match the name: field of the CI job. A typo in either place means the check is never satisfied — the merge button stays grey forever.

How — The Name Contract 
# In .github/workflows/ci.yml:
jobs:
  lint:
    name: Lint & Format (ruff)    # ← THIS EXACT STRING
  isort:
    name: Import Order (isort via ruff)  # ← THIS EXACT STRING

# In GitHub Settings → Branches → main → Required status checks:
# Search field: "Lint & Format (ruff)"  ← MUST MATCH EXACTLY
#               "Import Order (isort via ruff)"
# The search only shows checks that have run at least once on this repo.
# First: push a PR, let CI run, THEN add the checks to branch protection.
⚠️
Gotcha — The bootstrap problem

GitHub only shows status checks in the branch protection UI after they have run at least once on the repository. You cannot add a required check for a workflow that has never executed. The workflow order is: (1) push the CI workflow file, (2) open a PR to trigger it, (3) wait for the jobs to run, (4) go to Settings → Branches and add the named checks. If you add the check name before the job has run, GitHub accepts it as a string but it will never be satisfied (the check never ran = always pending).

4 · CODEOWNERS

What

A .github/CODEOWNERS file maps glob patterns to GitHub usernames or team names. When a PR touches a file matching a pattern, the mapped owner is automatically requested as a reviewer. When combined with branch protection's Require review from Code Owners, the owner's approval becomes a hard requirement — the merge is blocked until they approve.

# .github/CODEOWNERS for this repository
# Pattern evaluation: last matching pattern wins

*                               @karthikb35  # global fallback

# CI/CD configuration — highest security sensitivity
.github/                        @karthikb35  # any CI/workflow change requires review

# Study guide books
study-guide/                    @karthikb35

# Module notebooks
01-git-github-actions/          @karthikb35
02-jenkins/                     @karthikb35
# ... (all modules)
🔎
Why .github/ is the highest-priority CODEOWNER pattern

The .github/ directory contains workflow files, branch protection is defined here, and CODEOWNERS itself lives here. A malicious or carelessly-changed workflow can: (a) disable all security scans, (b) add commands that exfiltrate secrets via curl, (c) disable required checks. This is why the Codecov supply-chain attack was so effective — engineers trusted CI scripts without reviewing them. By requiring the repo owner's approval for any .github/ change, no workflow modification can be merged without expert eyes on it.

5 · Ruff — The All-in-One Linter

What

Ruff is a Python linter and formatter written in Rust. It implements rules from: pyflakes (F), pycodestyle (E/W), isort (I), pyupgrade (UP), flake8-bugbear (B), flake8-bandit (S), and 40+ other plugins — all in one binary, configured in ruff.toml, running in milliseconds.

Why ruff over flake8 + isort + bandit
  • Speed: 10–100× faster than Python-based tools. 100k-line codebase: ~200ms vs 20+ seconds.
  • Consolidation: One binary, one config, one CI step. No version conflicts between tools.
  • Auto-fix: ruff check --fix . auto-corrects hundreds of rules. Engineers fix issues without manual editing.
  • Formatter: ruff format replaces Black with identical output and 3× the speed.

6 · Import Order (isort via Ruff)

🧠
Mental Model — The Bookshelf

Imports are like books on a shelf. Isort enforces the library classification system: standard library books in section 1, third-party books in section 2, your own books in section 3. Within each section, alphabetical order. A shelf where medical books are mixed with cookbooks and computer science is technically functional but cognitively exhausting to navigate. Ordered imports are the same: technically unimportant to the interpreter, but enormously important for the engineer reading the file.

What

Isort defines the canonical order for Python import statements: (1) __future__ imports, (2) standard library (os, sys, json), (3) third-party packages (fastapi, pydantic), (4) local imports. Within each section: alphabetical. Groups separated by a blank line.

# ❌ BEFORE — isort violation, I001 rule fires:
import json
import os
from pathlib import Path        # standard library mixed up
import yaml                     # third-party before stdlib blank line
from dataclasses import dataclass
import sys

# ✅ AFTER — ruff check --select I --fix . auto-corrects this:
from __future__ import annotations

import json
import os
import sys
from dataclasses import dataclass
from pathlib import Path

import yaml
🔎
Why isort is a separate required check

Import order is a low-noise, high-signal check. If it fails, it means exactly one thing: someone added an import without running the formatter. This is almost always fixable in 2 seconds with ruff check --select I --fix .. By making isort a separate required check from the full lint check, you get two benefits: (1) the CI output clearly shows "import order failed" vs "security rule failed" — clearer diagnosis; (2) you can require isort independently of other lint rules — for repos where you're gradually migrating to ruff, you can require isort first before adding heavier rules.

7 · Protection Tests (pytest)

What

Protection tests are a pytest suite that checks the repository's structural health rather than application logic. They answer: are all notebooks valid JSON? Are workflow YAML files parseable? Does every job have a timeout? Is the CODEOWNERS file present? Do all HTML books have the required structure? These tests run on every PR and catch issues that would otherwise silently cause CI to behave unexpectedly.

Real-World: Airbnb's Repository Health Tests

Airbnb runs a suite they call "repository hygiene" tests — equivalent to this chapter's protection tests. They test: every Python package has a README.md, every service has an on-call contact documented, every workflow has an SLO alert configured, every Docker image has a Trivy scan result in the PR. These tests are required on every PR. The result: structural drift that used to be discovered during incidents (no on-call contact during an outage) is now caught during code review. The tests don't run application code; they enforce the meta-quality of the repository itself.

8 · GitHub Pages — Complete Deep Dive

🧠
Mental Model — The Always-On Website Living Inside Your Repo

GitHub Pages turns a directory of HTML/CSS/JS files inside your repository into a permanently hosted, HTTPS-secured website with zero infrastructure to manage. Think of it as a content delivery network that reads from your Git history. When you push a commit, the website updates. When you open a PR, GitHub can show a preview URL. When something goes wrong, you roll back the commit. The mental model: your website is a git branch — it has the same version history, the same review process, and the same branch protection you've configured for your code.

What

GitHub Pages is a static site hosting service built directly into GitHub. It serves files from your repository over HTTPS at a predictable URL. It supports raw HTML/CSS/JS (what we use), Jekyll (static site generator, runs automatically if a _config.yml exists), and custom domains. Crucially, the modern deployment path uses GitHub Actions — the same OIDC, concurrency, and environment-protection model we use for production deployments.

Why GitHub Pages instead of Vercel/Netlify/S3
  • Zero infrastructure: No S3 bucket, CloudFront distribution, or CDN config. No AWS account needed.
  • Same review flow: A PR to change the books also updates the live site — one workflow, one review cycle.
  • Free for public repos: No hosting cost, no bandwidth cap for public repositories.
  • OIDC deployment: Same passwordless credential pattern as AWS. No deploy keys stored anywhere.
  • Environment protection: Use GitHub Environments to require approval before the site updates.

The Two Deployment Sources — Legacy vs Modern

Branch-based deployment (legacy)

Source: a specific branch (e.g., gh-pages or main /docs folder).

Problems: no visibility into how the site was built, no CI gate before deploy, no OIDC, files must be committed into the branch manually or via a separate script, no concurrency control.

Still works but not recommended for new projects.

GitHub Actions deployment (modern)

Source: a GitHub Actions workflow using actions/upload-pages-artifact + actions/deploy-pages.

Benefits: full CI gate before deploy, OIDC token (no stored credentials), concurrency control, environment protection with optional manual approval, deployment URL shown in PR.

Setting: Settings → Pages → Source: GitHub Actions

The OIDC Pages Token Flow

Complete pages.yml — Annotated

# .github/workflows/pages.yml — full annotated reference
name: GitHub Pages — Study-Guide Site

on:
  push:
    branches: [main]
    paths:
      - "study-guide/**"          # only run when books change
      - ".github/workflows/pages.yml"
  workflow_dispatch:            # manual trigger for first deploy

# cancel-in-progress: false  → Pages deploys QUEUE, never cancel
# (unlike CI checks which cancel stale runs on new push)
concurrency:
  group: pages-${{ github.ref }}
  cancel-in-progress: false

# Minimum permissions for OIDC Pages deployment
permissions:
  contents: read   # read the repo
  pages: write     # upload Pages artifact
  id-token: write  # request OIDC JWT

jobs:
  build:
    runs-on: ubuntu-latest
    timeout-minutes: 10
    steps:
      - uses: actions/checkout@v4

      - name: Assemble _site/
        run: |
          mkdir -p _site
          cp study-guide/devops-path.css _site/
          cp study-guide/book-*.html     _site/
          cp study-guide/The-DevOps-Path.html _site/

      - name: Generate index.html
        run: python study-guide/build_index.py _site/

      # upload-pages-artifact packages _site/ as a Pages artifact
      # It must be a flat directory of static files (no symlinks)
      - uses: actions/upload-pages-artifact@v3
        with:
          path: _site

  deploy:
    needs: build
    if: github.event_name != 'pull_request'  # no deploy on PRs
    runs-on: ubuntu-latest
    timeout-minutes: 5

    # 'github-pages' is a RESERVED environment name.
    # GitHub creates it automatically when you enable Pages via Actions.
    # You can add protection rules to it in Settings → Environments.
    environment:
      name: github-pages
      url: ${{ steps.deployment.outputs.page_url }}  # shown in PR

    steps:
      - id: deployment
        uses: actions/deploy-pages@v4
        # This is the only step needed — the action handles the
        # OIDC token exchange with the Pages API internally.

Three Real Deployment Scenarios

Scenario A — Study guide site (this repo)
Trigger: push to main when study-guide/** changes. Build: copy HTML + CSS → _site/ → generate index.html. Deploy: actions/deploy-pages@v4. URL: karthikb35.github.io/DevOps-Path. No custom domain needed for a study repo.
Scenario B — Python library documentation (Sphinx/MkDocs)
Trigger: push to main when docs/** or src/** changes. Build: uv run mkdocs build → output to site/. Deploy: upload site/ as Pages artifact. Custom domain: docs.mylib.io. Add CNAME file during build step.
Scenario C — API reference (auto-generated)
Trigger: push to main (any file change — API may have changed). Build: run OpenAPI generator → static HTML. Deploy: Pages. Gates: test suite must pass first (needs: test before build). Ensures the API reference always reflects working code.

⚠️
Gotcha — Pages ignores files starting with underscore

Jekyll (the default GitHub Pages processor) skips all directories starting with _ (like _site/, _posts/). When using GitHub Actions deployment, Jekyll does NOT run — your files are served exactly as uploaded. But if you accidentally have a _config.yml in the root, GitHub may try to run Jekyll and transform your files. The safe pattern: (a) Use Actions deployment (not branch deployment), (b) Don't have a _config.yml unless you want Jekyll, (c) Add a .nojekyll file to the _site/ directory during build to explicitly disable Jekyll processing.

echo "" > _site/.nojekyll  # add this to the build step
🌍
Real-World: FastAPI's Documentation on GitHub Pages

FastAPI's documentation site (fastapi.tiangolo.com) is built with MkDocs and deployed to GitHub Pages on every commit to master. The workflow: pip install mkdocs-material → mkdocs build → deploy. The site has millions of monthly visitors, served entirely from GitHub's CDN. Cost: zero hosting infrastructure. Turnaround: documentation updates are live in under 2 minutes of merging a PR. This is the production-scale proof that GitHub Pages handles significant traffic without any configuration.

9 · uv — The Modern Python Package Manager

🧠
Mental Model — One Fast Tool Replacing Five Slow Ones

Before uv: pip to install, pip-tools to lock, virtualenv to isolate, poetry to orchestrate, and pyenv for Python versions. Five tools, five config files, five sources of drift. uv is a single Rust binary that replaces all of them and runs 10–100× faster. Built by Astral (the ruff company) with the same design philosophy: one opinionated tool that just works, fast.

What

uv manages Python installations, virtual environments, package installation, dependency locking, and project environments — all from one CLI. All operations share a global cache: installing the same package across 100 projects costs the disk space of one installation.

Why uv over pip + pip-tools + virtualenv

🔎
Commit uv.lock to Git — it is the reproducibility contract

The uv.lock file specifies the exact version and SHA hash of every package (including transitive dependencies). Without it: uv sync resolves fresh every run, which can produce different results on different Python patch versions. With it: every developer, every CI run, every Docker build uses an identical dependency graph. Add uv.lock to Git — add .venv/ to .gitignore.

10 · Senior Architect Interview Questions

Q1 · Describe the difference between a required status check and a pre-commit hook. Which is stronger, and why?

A pre-commit hook runs locally on the developer's machine and can be bypassed with git commit --no-verify. It provides fast feedback but is advisory. A required status check is enforced by GitHub's server-side API: if the check is failing, the merge button is disabled regardless of who is merging or what flags they use. The GitHub API enforcement is categorically stronger because it cannot be bypassed client-side. The correct pattern is both: pre-commit for developer speed (catches issues before they reach CI) and required status checks for repo safety (catches issues that bypass pre-commit).

Q2 · A team says "CI checks slow us down." How do you respond?

First, diagnose whether the complaint is about speed or about false failures. If speed: measure the actual wall time — most linting should complete in under 3 minutes, and the parallelism in the CI workflow means lint + tests + security all run simultaneously. If the slowness is tests, the right fix is faster tests (ruff replaces 5 tools with 1; protection tests run in seconds). If the complaint is false failures (flaky tests), fix the flakiness immediately — it erodes trust in all checks. The senior answer: "CI checks don't slow you down; they prevent the 4-hour incident caused by a 30-second fix that wasn't reviewed. The constraint is the value."

Q3 · Your company has 50 repositories. How do you enforce branch protection rules consistently across all of them?

GitHub Organization-level Rulesets (available in GitHub Teams/Enterprise). Instead of configuring branch protection per-repo, org owners define rulesets at the organization level that push down to all repositories. Repository admins cannot override org-level rulesets. This means: security team defines the minimum required checks, review count, and admin inclusion once — and every new repo automatically inherits it. Individual repos can add stricter rules on top of the baseline, but cannot remove the org-level minimum. For the open-source alternative: Terraform + the GitHub provider can manage branch protection as code, with PRs required to change it.

Q4 · A senior engineer argues that requiring their own CODEOWNER review on their own PRs is redundant. What's your response?

Two points: (1) Technically, CODEOWNER review requires someone else's approval — a CODEOWNER cannot approve their own PR when they are the author. GitHub enforces this. (2) More importantly, the review requirement is for accountability, not for the author's benefit. When you change the CI pipeline, you're changing a shared resource that affects every engineer on the team. The requirement that an expert reviews that change is not a comment on the author's competence — it's an acknowledgment that critical shared infrastructure deserves a second pair of eyes. This is the same principle as requiring two-key authorization for critical operations: not because either person is untrustworthy, but because the stakes justify the process.

Q5 · How do you handle the "bootstrap problem" — you can't add a required check until it has run at least once?

Two approaches: (1) Pragmatic: merge the CI workflow file directly to main (without the required check configured), let it run once on a simple PR, then add the required check. The check now exists in GitHub's system and can be required. (2) Principled: use a workflow_dispatch trigger on the CI workflow to run it manually against main without a PR — this creates the status check entry. Then add it to branch protection. For a new repository, approach (1) is acceptable since the required checks don't exist yet. For an existing repository, approach (2) avoids the awkward "merge without protection" step.

Chapter Takeaways
  • Social contracts fail under pressure; technical enforcement doesn't. Configure required checks and "Include administrators"
  • The check name in branch protection settings must exactly match the name: field in the CI job YAML
  • CODEOWNERS maps patterns to reviewers; combined with "Require Code Owner review" it becomes a hard gate
  • Ruff replaces flake8 + isort + bandit + black + pyupgrade with one binary, one config, ~200ms run time
  • Separate isort as its own required check — cleaner failure messages, independent gating
  • Protection tests check the repo's structural health: notebook JSON, workflow timeouts, CODEOWNERS existence
  • GitHub Pages uses OIDC — same pattern as AWS, no stored credentials, expires after job
  • Bootstrap order: push CI → trigger first run → add required checks in settings → verify with intentional violation
